Benchmarks

A benchmark is one standard in OSCAT's format: its controls, the checks each control runs, how the check results combine, and which controls depend on others. Benchmarks are YAML files (a profile.yaml), so they can be read, reviewed and kept in version control.

Getting a benchmark

OSCAT ships with no benchmarks: you decide what to audit against and add it yourself. On the Benchmarks page, Add benchmark takes a CIS benchmark PDF — OSCAT drafts a benchmark from it on the jumphost and publishes it so you can scan straight away, then you review the drafted checks whenever you like (Import a CIS PDF).

Managing benchmarks in the web app

The Benchmarks page lists each benchmark with its version, platform, number of controls and how many still need review (with a Review link to work through them). A benchmark still being read, or one that failed, shows there too until it finishes.

A benchmark's page lists its controls with levels, checks, dependencies and review state, and has the Offline collector button (Offline collector) and Download Excel: every control with its benchmark text in the report layout, with Status and Observation left empty to fill in by hand. Pick All controls or one of your control sets; a set's sheet holds only its controls and keeps their benchmark numbers.

Control sets

A control set is a named choice of a profile's controls, for example "ACME L1 servers", to reuse for scans and offline collectors. On the profile's page, + New control set opens the control picker: tick controls by section, search by number or title, or use the quick picks. Controls a ticked control depends on are added for you. The list shows how many controls each set runs and which scans and collectors use it; auditors can edit or delete a set. Scans and collectors already made from a set keep the controls they had.

Your own controls

Below the picker, + Add a control of your own lets you type in a control: a title, the command to run, and what output makes it pass (is exactly, contains, does not contain, matches a pattern, is empty or not empty, or the command succeeds). Add more than one check and all of them must pass. + Copy controls from another benchmark copies controls, with their checks, from another benchmark for the same platform.

Added controls join the benchmark under Custom controls, numbered C.1, C.2 and so on, and are ticked in the set you are editing. They are scanned, collected offline, reported and scored like any other control.

A set belongs to the benchmark, not to one upload, so it still works after you upload a newer version of the same profile. Controls the new version no longer has are ignored.

On the server: oscat-server import-profile <folder, .yaml or .zip>. To check a file for mistakes before uploading: oscat validate profile.yaml.

The format

profile:
  id: cis-ubuntu-22.04
  title: CIS Ubuntu Linux 22.04 LTS Benchmark
  benchmark: CIS Ubuntu Linux 22.04 LTS Benchmark
  version: 3.0.0
  platform: linux                      # linux | unix | windows | network | database | other
  os: {id: ubuntu, version: "22.04"}   # used by the offline collector
  sections: {"1": Initial Setup, "5": Access Control}

controls:
  - id: "1.1.1.1"
    title: Ensure cramfs kernel module is not available
    levels: [L1-server, L1-workstation]
    description: ...                   # CIS fields shown in reports:
    rationale: ...                     # impact, audit, remediation, default_value, references
    checks:
      - id: not_loaded
        run: lsmod | grep -w cramfs || true
        assert: {empty: true}
      - id: not_loadable
        run: modprobe --showconfig | grep -E '^\s*install\s+cramfs\b' || true
        assert: {any_line: {regex: '^\s*install\s+cramfs\s+/bin/(true|false)'}}
    logic: {and: [not_loaded, not_loadable]}

Checks

Each check collects one piece of evidence and judges it with an assertion.

Field Meaning
id name used in logic and shown in the evidence
run a command (or a multi-line script)
run_script a script file next to the profile, instead of run
shell sh (default), bash, powershell
privilege user (default) or root: run through privilege escalation
timeout seconds, default 60
assert the assertion (below); without one the check is evidence for a manual review

Windows checks (registry, secpol, user_right, auditpol, service) and APIC checks (rest) read settings directly instead of running a command; see Windows and Cisco APIC.

Assertions

Assertion Passes when
empty: true / not_empty: true the output is empty / not empty
equals, not_equals the trimmed output is exactly / is not the value
contains, not_contains the output contains / does not contain the text
regex, not_regex the regular expression matches / does not match
in_set: [a, b] the output is one of the values
exit_code: 0 (or a list) the command's exit code is one of them
num: {op: lte, value: 365, pattern: 'PASS_MAX_DAYS\s+(\d+)'} the number found compares (eq, ne, gt, gte, lt, lte)
mode_at_most: "0640" the octal mode in the output grants no more than this
contains_lines: [...] every listed line appears in the output
exact_lines: [...] the output has exactly these lines
every_line, any_line, no_line: {<assertion>} every / some / no output line passes the inner assertion
all_of, any_of: [...], not: {...} combine assertions

Options ignore_case: true and normalize_whitespace: true can sit beside an assertion.

Logic: controls with several results

logic combines the results of a control's checks. Without it, every check must pass.

logic: {and: [a, b]}                     # both pass
logic: {or: [a, b]}                      # either passes
logic: {not: a}
logic: {at_least: {count: 2, of: [a, b, c]}}
logic: {if: installed, then: disabled}   # only required when 'installed' passes
logic: {if: a, then: b, else: c}

A definite answer wins over an unknown one: an and with any failing check fails even if another check errored, and an or with any passing check passes.

Applicability and dependencies

  - id: "5.1.20"
    applicable_if: sshd_present          # N/A when this check (or logic) fails
    checks: [...]

  - id: "1.1.2.2"
    title: Ensure nodev option set on /tmp partition
    depends_on:
      - {control: "1.1.2.1", require: PASS, otherwise: NOT_APPLICABLE}

depends_on runs the control only when the named control reached one of the require states (default PASS); otherwise the control gets the otherwise state (default SKIPPED).

Manual controls and review

  • manual: true marks a control a person must judge; any checks still run as evidence.
  • review: needed marks a control nobody has checked yet (imported or converted controls). Results and reports flag them until the control is set to review: approved.

See profiles/examples/linux-demo.yaml for a complete example of every feature.

Custom controls are listed under their own "Your custom controls" heading on the benchmark page and are not part of a scan or an offline collector unless you tick Include custom controls when you start it (or pick a control set that contains them). Click any control to see its checks and the rule it must pass.
